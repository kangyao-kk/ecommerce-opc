# 项目基准（Project Charter）

> 本文件是后续所有技术选型、目录设计、功能开发和代码评审的共同基准。
> 任何与本文冲突的临时决策，都应以本文为准，或先修订本文再执行。

## 0. 一句话定位

我们要构建一套以 Python 和 FastAPI 为工程底座、以 AG2 为 Agent 协作引擎、
以真实电商业务为驱动的 AI 原生运营系统。
它既是探索商业化 SaaS 的产品原型，也是能证明后端工程与 Agent 工程综合能力的长期项目。

我们不是在做 AI Agent Demo，也不是为了学习 AG2 而搭多 Agent 聊天系统。

---

## 1. 核心定位

| 维度 | 定位 |
|---|---|
| 业务 | AI 辅助运营电商 OPC 公司，面向真实经营场景 |
| 技术 | Python 后端工程 + Agent 工程（FastAPI + AG2） |
| 产品 | 从自用系统演进为 SaaS 平台，早期预留边界，不做过度设计 |
| 个人 | 从传统后端工程师成长为后端 + Agent 工程师 |

---

## 2. 两个最终目标（共用同一套技术底座）

### 方向 A：可商业化的 SaaS 产品
- 以真实业务需求决定功能优先级。
- 逐步形成可配置、可复用的业务模块。
- 预留多租户、权限控制、数据隔离和订阅计费能力。
- 用实际业务结果验证产品价值和商业模式。

### 方向 B：高质量的个人工程项目
- 规范的 Python 项目初始化与工程结构。
- FastAPI 服务设计、数据库建模和 API 设计。
- AG2 多 Agent 协作与工具调用。
- 任务状态管理、异常恢复、日志、测试和部署。
- 从业务需求到架构设计再到实际交付的完整能力展示。

**策略：** 先做出能解决真实问题的系统，再让它具备复制和商业化能力。
不为了未来可能的需求提前把系统设计得过于复杂——架构要能演进，而不是一开始就建成庞大平台。

---

## 3. FastAPI 与 Agent 的关系

本项目本质上是一个**后端业务系统**，只是其中一部分业务能力由 Agent 驱动。

逻辑架构（分层，而非要求每层独立部署）：
业务入口与应用接口
FastAPI · REST API · 身份认证 · 请求校验
↓
应用层与业务服务
用例编排 · 业务规则 · 任务管理 · 权限校验
↓
┌──────────────────────┬──────────────────────┐
│ 传统业务能力 │ Agent 业务能力 │
│ 确定性流程、数据查询、 │ 复杂任务分解、信息分析、│
│ 订单处理、状态变更、 │ 工具选择、多 Agent 协作│
│ 规则校验 │ │
└──────────────────────┴──────────────────────┘
↓
基础设施与外部系统
数据库 · 缓存 · 消息队列 · 电商平台 API · 大模型服务

text

**必须遵守的原则：**
- FastAPI 负责服务入口，不负责所有业务逻辑。
- 业务服务负责业务规则，不应把所有规则塞进 Agent Prompt。
- AG2 负责需要智能决策或多 Agent 协作的任务，不应替代整个后端。
- 数据库负责可靠持久化，不应把数据库当成 Agent 的记忆替代品。
- Agent 执行结果必须经过业务规则校验；关键操作还要有权限校验和必要的人工确认。

例：AI 可以分析哪些商品值得优先推广，但预算修改、价格变更、订单操作
应由受控的业务服务执行，而不是让模型任意操作数据库。

**目标形态：** 有智能能力，但依然具备传统软件工程可靠性的系统。

## 4. 技术栈与工程原则

### 4.1 技术选型方向（非一次性安装清单）

| 领域 | 技术方向 | 职责 |
|---|---|---|
| 编程语言 | Python | 核心开发语言 |
| 项目与依赖管理 | uv | 初始化项目、管理依赖、锁定环境 |
| Web 后端 | FastAPI | HTTP API、请求校验、依赖注入 |
| Agent 框架 | AG2 | 多 Agent 协作、任务编排、工具调用 |
| 数据校验 | Pydantic | 请求模型、配置模型、结构化数据 |
| 关系型数据库 | PostgreSQL | 业务数据、任务记录、运营数据 |
| 数据访问 | SQLAlchemy | ORM、事务和查询 |
| 数据库迁移 | Alembic | 可追踪、可回滚的 Schema 演进 |
| 测试 | pytest | 单元测试、集成测试、业务流程验证 |
| 工程质量 | Ruff、类型检查工具 | 格式、静态检查和代码质量 |
| 部署 | Docker | 可重复构建和运行环境 |

Redis、消息队列、向量数据库、对象存储、独立 Agent Worker 等组件，
**等实际需求出现时再引入**。具体版本、组件和目录边界在项目初始化阶段结合当前 AG2 API 与业务需求确定。

### 4.2 工程原则（参照《代码整洁之道》）

1. **简单优先。** 不为设计模式而设计，不引入不必要的抽象。
2. **职责清晰。** API、业务逻辑、Agent 编排、数据访问各有明确边界。
3. **依赖可控。** 业务核心不被具体模型供应商或 Agent 框架 API 绑死。
4. **显式优于隐式。** 关键配置、业务状态、任务输入和执行结果都有明确数据结构。
5. **可测试。** 核心业务规则不必启动整个系统或调用真实大模型即可测试。
6. **可靠性优先。** 关注超时、重试、幂等性、失败恢复、任务追踪和权限边界。
7. **渐进式架构。** 从模块化单体开始，只在出现明确扩展/隔离需求时才拆分服务。

可参考开源项目的架构思想与设计经验，但代码、领域模型和业务流程必须服务于自己的产品需求。

## 5. 我们开发的是业务工作流，不是聊天机器人

若系统只能"用户提问 → 多 Agent 讨论 → 生成回答"，其商业价值和工程深度都有限。

真正需要的是让 AI 参与完整业务闭环：
01 获取业务信息 读取商品、订单、市场和运营数据
02 理解业务目标 明确任务、约束、输入和预期结果
03 分析与规划 Agent 分析问题并制定执行计划
04 调用业务工具 通过受控接口执行查询、生成和操作
05 验证执行结果 校验结果、处理异常，必要时请求人工确认
06 沉淀执行记录 记录状态、结果、成本和后续改进信息

text

**功能完成的验收标准：** 不只看能否给出答案，还要看能否可靠地获取信息、
调用工具、处理失败，并产出真正可用于业务的结果。

**多 Agent 不是目标本身。** 只有当不同角色确实需要不同的上下文、工具权限、
专业职责或并行执行能力时，才拆分多个 Agent。简单任务用普通 Python 函数或单 Agent 往往更易维护。

## 6. 推进阶段

1. **工程初始化与架构骨架** — uv init、目录结构、配置、日志、异常、测试规范、FastAPI 入口。
2. **选择一个真实电商运营场景** — 高频、可衡量、适合 AI 介入；设计输入、输出、业务规则、数据模型、验收标准。
3. **打通完整业务闭环** — API → 应用服务 → Agent/业务逻辑 → 工具调用 → 持久化 → 可验证结果。
4. **建立可靠的 Agent 执行机制** — 任务状态、超时、重试、幂等、执行日志、人工审批、评估机制。
5. **抽象可复用的业务模块** — 多个相似场景出现后再抽象公共工具、Agent 能力、工作流模板和业务服务。
6. **逐步产品化和商业化** — 租户隔离、权限、运营后台、配额、计费、部署方案。

---

## 7. 验收维度

| 维度 | 判断标准 |
|---|---|
| 业务价值 | 是否解决真实问题，是否节省时间或改善经营结果 |
| 工程质量 | 是否职责清晰、易测试、易维护、易扩展 |
| Agent 能力 | 是否真正完成复杂任务，而不只是生成文本 |
| 系统可靠性 | 失败是否可观测、可恢复，重复执行是否安全 |
| 产品化能力 | 能否在不改核心代码的情况下适配不同客户 |
| 个人成长 | 能否解释每项架构决策、权衡及实际收益 |

SaaS 的多租户、权限和数据隔离不能等产品卖出去才考虑，但也不必第一天就实现完整计费系统和企业级权限平台。
**做法：** 早期为关键边界留出合理设计，业务验证后再逐步完善。

---

## 8. 协作方式

按真实工程团队的方式协作，而不是一次性生成大量代码后被被动接收。

**分工：**
- 我（协作者）：业务需求拆解、技术方案设计、项目结构与模块边界、组件集成、
  核心代码实现、测试设计、代码审查、问题排查、架构演进与 SaaS 规划。
- 你（项目所有者）：逐步掌握每个模块为什么存在、为什么这样设计、在真实项目中如何取舍。

每一阶段都要有明确的交付物和验收标准。
不为了炫技使用复杂架构，也不为了快速出 Demo 放弃基本工程规范。

**节奏：** 先把业务做对 → 再把工程做稳 → 最后把能力做成产品。

---

## 9. 当前优先事项

不需要一开始就解决所有电商运营问题。首先：

1. 建立一个优雅、可靠、可演进的工程骨架。
2. 选择一个真实业务场景。
3. 把它从需求一直做到可运行、可测试、可验证的完整闭环。
